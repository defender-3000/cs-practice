# Шпаргалка по командам анализа в Git

### 1. В чём разница: git diff vs git show vs git log?

* **`git diff`** — показывает **текущие незакоммиченные изменения**. Это разница между вашим рабочим каталогом и последним сохранённым состоянием (индексом или коммитом). Отвечает на вопрос: *"Что я изменил в файлах прямо сейчас?"*
* **`git show`** — показывает **содержимое конкретного объекта** (обычно коммита). Вы увидите автора, дату, сообщение коммита и детальный список изменений (diff) конкретно для этого шага истории. Отвечает на вопрос: *"Что именно было сделано в этом конкретном коммите?"*
* **`git log`** — показывает **историю коммитов** в виде списка. Он выводит хэши, авторов, даты и сообщения коммитов, но по умолчанию не показывает изменённые строки кода. Отвечает на вопрос: *"Какова хронология разработки проекта?"*

---

### 2. Что делают специальные команды поиска?

* **`git log -S "текст"`** (Поиск "Кирка" / Pickaxe) — ищет коммиты, в которых указанная строка текста **появилась или исчезла** из файлов. Это незаменимо, если вам нужно найти, когда именно в проект добавили конкретную функцию или удалили важную переменную.
* **`git blame <файл>`** (Построчный анализ) — показывает выбранный файл построчно, выводя слева от каждой строки **автора, дату и хэш коммита**, который эту строку изменил последним. Отвечает на вопрос: *"Кто, когда и в каком коммите написал или отредактировал эту конкретную строчку кода?"*


### 3. Разница между git restore и git restore --source=...

* **`git restore <файл>`** — сбрасывает изменения в файле до состояния **последнего коммита** (из текущей ветки).
  * **Что произойдет с вашими правками:** Все текущие незакоммиченные изменения в этом файле будут **безвозвратно удалены**. Файл вернется к тому виду, в каком он был на момент последнего сохранения (`HEAD`).

* **`git restore --source=<хэш_коммита_или_ветка> <файл>`** — извлекает состояние файла из **конкретной точки истории** (старого коммита или другой ветки) и копирует его в ваш рабочий каталог.
  * **Что произойдет с вашими правками:** Ваши текущие локальные правки в этом файле будут **заменены (перезаписаны)** кодом из указанного вами старого коммита. При этом сама история проекта не изменится — старый код просто запишется в ваш текущий рабочий файл как новая незакоммиченная правка, которую вы потом сможете закоммитить.

**Важно:** Обе команды являются «опасными», так как они перезаписывают файлы в рабочей папке. Если вы не закоммитили свои текущие правки перед их запуском, вернуть их обратно стандартными средствами Git будет невозможно.


### 4. Отмена изменений: git restore vs git reset --hard

Команда **`git reset --hard <коммит>`** кардинально отличается от `git restore`. Она перемещает указатель вашей текущей ветки назад в истории.

* **`git restore <файл>`** — работает на уровне **отдельного файла** в рабочей области. История коммитов при этом вообще не двигается и не меняется.
* **`git reset --hard`** — работает на уровне **всего репозитория и его истории**. Она стирает коммиты, перематывая ветку назад, и одновременно уничтожает все незакоммиченные правки.

### 5. Почему в опубликованной истории безопаснее использовать git revert?

Когда вы уже отправили коммиты на GitHub (в опубликованную историю), использовать `git reset --hard` становится **опасно**, и вот почему:

1. **`git reset --hard` переписывает историю.** Если вы удалите коммит у себя локально и попытаетесь сделать `git push`, GitHub отклонит изменения. Вам придётся использовать принудительную отправку (`git push --force`).
2. **Это ломает работу коллегам.** Если кто-то из вашей команды уже скачал (`git pull`) те коммиты, которые вы стёрли с помощью `reset`, их локальная история разойдётся с удалённой. При следующем обновлении удалённые вами коммиты могут снова «прилететь» обратно или создать сложные конфликты слияния.

#### Решение: `git revert <хэш_коммита>`
Вместо удаления коммита из истории, `git revert` создаёт **новый, компенсирующий коммит**. Он делает противоположные действия: если в старом коммите строка была добавлена, `revert` её удалит.

* **Безопасность:** История проекта движется только вперёд. Никакие прошлые коммиты не стираются.
* **Совместимость:** Команда создаёт обычный коммит, который без проблем отправляется на GitHub (`git push`) без всяких `--force` и не ломает историю вашим коллегам.

### 6. В чём разница: Тег (Tag) vs Ветка (Branch)?

Хотя и тег, и ветка являются «указателями» на конкретные коммиты, их поведение и цели принципиально отличаются:

* **Ветка (Branch) — это динамический указатель.** Она постоянно движется вперёд. Когда вы находитесь на ветке и делаете новый коммит, указатель ветки автоматически перемещается на этот самый свежий коммит. Ветки нужны для активной разработки и изоляции новых фич.
* **Тег (Tag) — это статический указатель («снимок во времени»).** Он навсегда остаётся привязанным к тому коммиту, на который его установили. Даже если вы продолжите делать новые коммиты в этой ветке, тег не сдвинется с места. 

#### Главное отличие одной фразой:
Ветка создаётся для **изменений** и движется вместе с кодом, а тег создаётся для **фиксации результата** (например, стабильной версии `v1.0.0`) и остаётся неизменным, позволяя легко найти нужную версию проекта даже спустя полгода.
